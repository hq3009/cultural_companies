# 数据库与表关系梳理

依据 `数据来源台账_2025-08-29.xlsx`（11 个分层页）与 `金融主题库字段表_20250715.xlsx`（目录、指标、编号字段页），代码字典参照 `核准主体表字段表.xlsx`；对照脚本 `src/culture_2026.sql`。只记关系要点，字段明细仍以原表为准；字段表存在中文字段名错标，行业两列按现场确认的实际内容使用。

## 一、分层链路

| 层级 | 台账中的位置 | 表名形态 | 与脚本的关系 |
| --- | --- | --- | --- |
| 采集渠道 | 数据来源渠道、RDS 源表两页 | 部门库、接口、批量文件 | 不在上游取数 |
| 贴源层 | 贴源层 | `v_ods_` / `v_stg_` / `stg_` 前缀 | 不直接读取 |
| 标准层 | 标准层、字段表目录 | `DW_*`，位于 `odps_jrsjc_pod` | 唯一数据来源，脚本引用 14 张 |
| 主题层 | 主题层（专题库按表） | `DW_NB_TLDW_*` | 脚本未用 |
| 应用层 | 应用层（指标+模型）、指标 | `INDEX_*`、`DESEN_INDEX_*` | 脚本未用，可作为现成指标来源 |
| 对外 | 接口、共享、开放 | 模型服务、脱敏指标表 | 与本次分析无直接关系 |

脚本在 `jrsjc_dev` 另起一条轻链路，不依赖主题层与应用层：

主链：`industry_codes` → `company` → `company_core` → 13 张 `company_*` → `company_profile` → `selection_pool` → `selection_ranked` → `selected_top3000`

旁路：`company` → `rpt_wenlv`（只抽 8 个登记字段）；`company_profile` 直接支撑 SECTION 4、5 的统计查询。

## 二、关系要点

### 1. 依赖：谁由谁生成

- 贴源层 → 标准层：标准层的“源表名”指向贴源层同名表（台账中 255 张标准表有 238 张可对应），属一对一归集加字段标准化。字段表目录另给出 `源数据库`（`nb_dw_pod` / `nb_dl`）与 `ODPS_表英文名`。
- 标准层 → 主题层：主题层“来源标准表”列用 `&` 表示合并，例如工商信息表 = `DW_NB_TLDW_GSXX` & `DW_ZJ_SCJDGL_SCZTXX`，公司工商异常表 = `DW_NB_TLDW_GSGSYC` & `DW_ZJ_SCJDGL_JYYCMLXX`，公司违法信息表 = `DW_NB_TLDW_GSWFXX` & `DW_ZJ_SCJDGL_YZWFSX`。即业务系统存量表与省回流标准表拼装，同名的 `DW_NB_TLDW_*` 是存量表而非同一张表。
- 标准层 → 应用层：字段表目录中 `对应指标表名`（`INDEX_*`）与 `对应脱敏指标表名`（`DESEN_INDEX_*`）成对出现；台账应用层、共享、开放页列的是脱敏结果表，共享页 31 张表标注来源层为应用层。指标页主键写作 `PRIPID,ENTNAME,CREDIT_CODE`，与标准层 `MAIN_IDENTI_ID`（源字段 `pripid`）、`COMP_NM`、`UNI_SOCIAL_CRD_CD` 是同一批键的不同命名。
- 脚本内部：代码表定筛选范围，`company` 定企业全集，`company_core` 定基准字段，各扩展表平行依赖 `company_core` 加一张标准表，`company_profile` 依赖全部扩展表；统计与遴选以 `company_profile` 为源，`rpt_wenlv` 是绕开宽表、直取 `company` 的旁路。

### 2. 共用字段：关联口径

- 主关联键是 `UNI_SOCIAL_CRD_CD`。脚本引用的 14 张标准表中 13 张带该字段，扩展表预聚合、宽表拼接、遴选关联全部用它。
- `PRIPID` 在年报、处罚、股权变更、担保等市市场监管表中共存，可作备用键；`COMP_NM` 几乎各表都有，但属名称，不是稳定键；主体表另有 `MAIN_IDENTI_ID`、`LV_PRIPID`。
- 弱关联例外：`dw_nb_kj_sgczkjxzxqy`（省高成长科技型中小企业）只有 `COMP_NM`，脚本 3.14 用 `TRIM(comp_nm)` 匹配；`dw_zj_fzgg_sxbzxrxx`（失信被执行人）企业记录与个人记录混存，字段表目录为它分出 `_COMP` 与 `_PERSON` 两张指标表，需按信用代码过滤。
- 时间列各表自成一套：主体表 `APPR_DT`（核准日期），经营异常 `INCLU_DT` / `REMOVE_DT`，严重违法 `ABN_TM` / `REM_DT`，年报类 `ANNUAL_YEAR`，纳税 `COUNT_DT`，社保 `*_PAY_YM` / `ISSUE_START_DT`，信用评价 `EVALU_DT` / `EVALU_YEAR`。取“最新一条”必须按本表时间列，不能套用主体表的 `appr_dt`。
- `核准主体表字段表.xlsx` 提供 `opstate`（企业状态，除 D、DA、C、Z 外在册）、`enttype` / `qylxdl`（企业类型）、`domdistrict`（行政区划）、`industryphy` / `industryco`（行业）等编码字典；字典注明 `industryco` 可能为空，需用 `industryphy` 补门类。
- 主体表两个行业字段的实际内容与字段表中文字段名相反，已在操作现场确认：`INDV_NM` 存四位阿拉伯数字行业代码，`INDV_ID` 存中文行业名称。筛选统一用 `indv_nm` 与 `industry_codes.indv_nm` 匹配，不以字段名或字典标注推断口径。

### 3. 扩展：平行加列

- 13 张 `company_*` 互不依赖，都以 `company_core` 左连一张标准表的预聚合结果，输出次数、最新值、财务值、名单标签几类增量列。
- 预聚合套路固定：`COUNT(*)` 生成 `*_count`；`ROW_NUMBER()` 按 `uni_social_crd_cd` 分区、按本表时间列降序并带 ID 类第二排序键，取 `rn = 1` 生成 `latest_*`；年报类按 `ANNUAL_YEAR` 取最新。
- 源表时效差异大：主体表约 310 万条且每日更新，企业年报资产信息止于 2019 年且不更新，行政处罚止于 2021 年，社保按月更新。扩展列为空多数反映源表未覆盖或已停更，不宜解释为企业无该事项。

### 4. 继承：字段复制与裁剪

- `company` → `company_core` 是字段裁剪，保留主体身份、行业、区划、登记状态等基准属性。
- `company_core` → `company_*` 目前是 `SELECT core.*, ...`，每张扩展表都复制全套核心字段；`company_profile` 又从 `company_core` 出发，按信用代码把 13 张已建扩展表拼回（另左连尚未创建的 `company_fddb`）。核心字段被复制 13 份，是主要的冗余来源。
- 建议的继承结构：扩展表只保留 `uni_social_crd_cd` 加本主题增量列，`company_profile` 从 `company_core` 取基础列、左连各扩展表的增量列。基准字段只存一处，也顺带降低宽表一对多膨胀的风险。

## 三、对 `culture_2026.sql` 建表逻辑的提示

1. 依赖顺序宜固定为：代码表 → 基准表 → 并行扩展表 → 宽表 → 报表与遴选；宽表必须等所有被左连的表建成后再建。目前 `company_profile` 左连了 `company_fddb`，脚本中却没有建这张表，台账标准层的 `DW_ZJ_SCJDGL_FDDBRXX`（法定代表人信息）可作来源，属于待补的依赖缺口。
2. `company` 的字段清单需与 `company_core` 的引用核对：`uni_social_crd_cd addr` 疑为缺逗号导致别名错位，`reg_state` 重复，SELECT 末行多一个逗号。继承链从这里开始，字段对不上会逐级传导。
3. 行业筛选口径以现场确认为准：`indv_nm` 是四位阿拉伯数字行业代码，`indv_id` 是中文行业名称，字段表两列的中文字段名标反了。脚本按 `indv_nm` 与 `industry_codes` 匹配符合实际口径，不要按字段表标注改用 `indv_id`；SECTION 0 的形态检查与 1.2 的匹配数校验用于确认当前数据取值形态和覆盖率。
4. 弱关联表（按名称匹配）与精确关联表（按信用代码匹配）应分开标注，避免把名称匹配结果计入精确命中口径。
5. 各扩展表去重排序键要逐表按自身时间列确认，主体去重只按 `appr_dt` 单键；两者不是同一套规则。
6. 若后续允许使用应用层表，`DESEN_INDEX_*` 已有经营异常次数、近 1 年及 3 年次数、存续时长、企业性质等脱敏指标，可省去部分自行聚合。当前脚本只取标准层，口径自洽，不必为此改动。
